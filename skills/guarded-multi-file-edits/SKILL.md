# 多檔案保守修改規範

當使用者要求以下類型工作時使用這個技能：
- 優化
- 重構
- 多檔案清理
- 大範圍一致性調整
- 任何一旦出錯就可能擴散到多個檔案的改動

## 不可違反的規則

1. 一次只能修改一個檔案。
2. 該檔案修改完成後，必須先驗證通過，才能動下一個檔案。
3. 如果驗證失敗，必須立即停止往外擴散。
4. 在目前檔案被確認安全之前，不得繼續處理下一個檔案。
5. 未經使用者明確同意，不得還原、覆蓋、替換或回退任何 Git 上的安全版本。
6. 未經使用者明確同意，不得 commit、amend、push、reset、restore、checkout，或以其他方式變動 Git 歷史或狀態。
7. 即使多個檔案看起來改法一樣，也不可以一次全部改完。

## 必須遵守的流程

處理多檔案任務時，一律依照以下順序：

1. 先檢查目標檔案，選出最小、最安全的起點。
2. 只修改第一個檔案。
3. 只針對該檔案執行最小但足夠的驗證。
4. 回報驗證結果。
5. 只有在這一步成功後，才能進入下一個檔案。

## 驗證標準

使用最小、但足以證明目前檔案安全的驗證方式，例如：
- `python -m py_compile <file>`
- 該檔案對應的單一測試
- 只針對該檔案的 lint
- 只針對該功能的最小 smoke test

不要因為「其他類似檔案已經通過」就跳過驗證。

## 失敗處理

如果某個檔案修改後驗證失敗：
- 立即停止
- 不得繼續修改下一個檔案
- 先修好同一個檔案，或請使用者決定下一步

如果修復動作會碰到 Git 上的安全版本：
- 必須先停下來，取得使用者明確同意

## Git 安全規範

目前已提交版本，以及任何已知安全的工作狀態，都應視為受保護內容。

未經使用者明確同意，不得：
- `git restore`
- `git checkout`
- `git reset`
- 用另一個版本覆蓋目前檔案
- 用歷史版本重建檔案
- 提交目前工作
- 修改既有 commit
- 推送到遠端

如果使用者要求這些操作，必須先確認範圍，只執行被明確批准的內容。

## 溝通方式

套用這個技能時：
- 要告訴使用者你現在只在改哪一個檔案
- 要說明你下一步會跑什麼驗證
- 如果停住，要明確說是哪個檔案卡住

## 正確範例

範例流程：

1. 先看三個候選檔案。
2. 選風險最低的一個。
3. 只修改那一個檔案。
4. 跑該檔案的驗證。
5. 回報結果。
6. 只有成功後才進下一個檔案。

## 禁止做法

不要：
- 先改五個檔案，最後才一起測
- 因為改法看起來一樣，就假設所有檔案都安全
- 靜默從 Git 還原檔案
- 未經同意就提交「整理類」工作
